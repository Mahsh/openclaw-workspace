# AVS标准提案分析：基于云手机RTP扩展交底书的标准提案路径

> 日期：2026-07-02
> 目的：分析如何将专利交底书抽象为AVS标准提案，评估是否需要修改交底书

---

## 一、AVS标准体系与云手机的对接点分析

### 1.1 AVS相关标准对照

从AVS已发布和制定中的标准来看，与本方案直接相关的有：

| AVS标准 | 名称 | 与本方案的关系 | 对接难度 |
|---------|------|--------------|---------|
| **GB/T 33475.6-2024** | 高效多媒体编码 第6部分：智能媒体传输 | **最相关**。定义了封装格式、传输协议和信令信息，用于异构包交换网络下的多媒体传输 | ⭐⭐ 可在此标准框架内扩展 |
| GB/T 33475.1-2019 | 高效多媒体编码 第1部分：系统 | 面向IP网络的自适应流媒体传输 | ⭐⭐⭐ 偏点播/直播场景 |
| T/AI 109.1（制定中） | 智能媒体编码 第1部分：沉浸媒体系统 | 定义VR视频/音频的封装、传输和信令格式 | ⭐⭐ 实时交互场景有交集 |
| T/AI 109.10-2024 | 智能媒体编码 第10部分：实时通信语音编码 | 实时通信方向 | ⭐ 仅语音 |
| AVS1第8部分（待颁布） | 在IP网络上传输AVS | IP网络传输AVS码流 | ⭐⭐⭐ 偏传统传输 |

### 1.2 AVS工作组结构

AVS工作组下设多个专题组，与本方案相关的：

- **系统组**：负责系统架构、传输协议、封装格式 → **主投方向**
- **视频组**：负责视频编解码算法 → 不涉及（你们不做编解码）
- **音频组**：不涉及
- **需求组**：负责需求定义和应用场景 → 可提交需求文档

### 1.3 核心判断

> **专利交底书 ≠ AVS标准提案。**
> 
> 专利是保护"我们的独特实现方案"，强调新颖性和创造性。
> 标准提案是定义"行业通用规范"，强调通用性、互操作性和可推广性。
> 
> 两者目标不同，写法不同，但**技术内核可以共享**。

## 二、专利交底书 vs 标准提案的差异

| 维度 | 专利交底书 | AVS标准提案 |
|------|-----------|------------|
| **目标** | 保护独有技术，获得排他性权利 | 定义行业规范，推动标准化 |
| **受众** | 专利审查员 | AVS工作组成员（竞品公司、科研院所） |
| **写法** | 强调"区别于现有技术的创新点" | 强调"通用性、可推广性、与现有标准的兼容性" |
| **技术粒度** | 实现细节（算法、数据结构、流程图） | 协议规范（字段定义、语法语义、合规性要求） |
| **排他性** | 越独特越好，希望别人绕不开 | 越通用越好，希望大家都采用 |
| **术语** | 可以用自定义术语 | 必须使用标准术语体系（如RTP/RTCP/SDP的RFC标准术语） |
| **引用** | 引用专利文献 | 引用RFC、ISO/IEC、GB/T等标准文献 |

### 2.1 需要修改的关键点

#### 差异1：去除"云手机"业务限定

专利可以限定在"云手机"场景，但标准提案需要**泛化**为更通用的技术框架。

```
专利写法:  "面向云手机交互式流媒体..."
标准写法:  "面向交互式远程渲染流媒体系统..."
```

泛化后的适用范围：云手机、云游戏、云桌面、远程渲染、XR远程呈现等。

#### 差异2：去除具体实现细节

专利需要详细的实现方案（如"滑动窗口500ms"、"SurfaceFlinger postFrame钩子"），但标准只定义**协议格式和语义**，不限定实现方式。

```
专利写法:  "云端维护一个滑动时间窗口（默认500ms），统计窗口内的指令类型和频率..."
标准写法:  "交互模式标识字段用于指示当前帧对应的交互类型，其取值定义见表X。
            具体的分类算法由实现方自行决定。"
```

#### 差异3：增加合规性定义

标准需要定义**MUST/SHALL/MAY/SHOULD**等级别的合规性要求，专利不需要。

```
标准要求:
  - 发送端 SHALL 在每个RTP包的头部扩展中携带交互模式标识
  - 接收端 MUST 支持解析交互模式标识字段
  - 发送端 MAY 在弱网条件下省略非关键字段
```

#### 差异4：增加互操作性考量

标准需要考虑不同厂商的实现能否互通：

- 字段值的注册和扩展机制（IANA-style registry）
- 向前/向后兼容性（旧终端遇到新字段怎么办）
- 与现有RTP扩展的共存（不能和已有的Header Extension冲突）

#### 差异5：增加参考标准引用

标准提案需要引用相关RFC和标准：

- RFC 3550 (RTP)
- RFC 8285 (RTP Header Extension)
- RFC 4585 (RTCP Feedback)
- RFC 8825 (WebRTC Overview)
- GB/T 33475.6-2024 (AVS2 智能媒体传输)

## 三、标准提案建议方案

### 3.1 提案拆分建议

建议将专利交底书的内容拆分为**3个层次**的标准产出物：

```
层次1: 需求文档（轻量级，容易通过）
  └── 《交互式远程渲染流媒体传输需求》

层次2: 技术报告（中等难度，提供技术背景）
  └── 《交互式远程渲染流媒体传输技术报告》

层次3: 标准规范（最核心，需要长期推进）
  └── 《智能媒体传输 第N部分：交互式远程渲染传输协议扩展》
```

### 3.2 层次1：需求文档

**标题：** 《交互式远程渲染流媒体系统传输需求》

**内容大纲：**

```
1. 范围
2. 术语和定义
3. 缩略语
4. 应用场景
   4.1 云手机
   4.2 云游戏
   4.3 云桌面/远程渲染
   4.4 XR远程呈现
5. 系统架构模型
   5.1 非对称双链路模型
   5.2 控制链路与媒体链路的分离
6. 传输需求
   6.1 端到端交互延迟需求
   6.2 交互模式感知需求
   6.3 上行通道状态反馈需求
   6.4 弱网自适应需求
   6.5 场景化播放策略需求
7. 与其他标准的关系
   7.1 与GB/T 33475.6（智能媒体传输）的关系
   7.2 与RFC 3550/8285（RTP）的关系
8. 安全考量
```

**价值：** 需求文档是标准制定的第一步，门槛最低，但能为后续标准规范"占位"。

### 3.3 层次2：技术报告

**标题：** 《交互式远程渲染流媒体传输技术报告》

**内容大纲：**

```
1. 引言
2. 技术背景
   2.1 交互式远程渲染系统架构
   2.2 现有RTP/WebRTC传输机制的局限性
3. 关键技术问题分析
   3.1 控制-媒体链路信息割裂问题
   3.2 终端播放策略缺乏场景感知问题
   3.3 上行通道状态不可见问题
   3.4 云端处理延迟对拥塞控制的干扰问题
4. 技术方案综述
   4.1 RTP头部扩展元数据注入方案
   4.2 字段定义与语义
   4.3 SDP协商机制
   4.4 冗余保护与容灾机制
5. 实验数据与性能评估
6. 与现有技术的比较
7. 结论与建议
```

**价值：** 技术报告不定义规范，但提供了详细的技术分析和实验数据，为标准规范提供技术支撑。

### 3.4 层次3：标准规范（核心）

**标题建议：** 《智能媒体传输 补充件：交互式远程渲染传输协议扩展》

或作为GB/T 33475.6的增补件提交。

**内容大纲（标准规范格式）：**

```
1. 范围
   本标准规定了交互式远程渲染流媒体系统中，基于RTP协议的传输扩展字段定义、
   信令协商机制和合规性要求。

2. 规范性引用文件
   - RFC 3550
   - RFC 8285
   - RFC 4585
   - GB/T 33475.6-2024

3. 术语、定义和缩略语
   3.1 交互式远程渲染系统 (Interactive Remote Rendering System)
   3.2 控制链路 (Control Link)
   3.3 媒体链路 (Media Link)
   3.4 交互模式标识 (Interaction Mode Identifier)
   3.5 帧意图标记 (Frame Intent Tag)
   ...

4. 系统模型
   4.1 参考架构
   4.2 控制链路与媒体链路分离模型
   4.3 交互数据流模型

5. RTP头部扩展定义
   5.1 扩展格式
       - 交互模式标识字段 (Interaction Mode ID)
       - 指令序列号锚点字段 (Command Sequence Anchor)
       - 帧意图标记字段 (Frame Intent)
       - 上行状态反馈字段 (Uplink Status Feedback)
   5.2 字段语义与编码规则
   5.3 字段值的注册与扩展机制（Registry）

6. 信令协商
   6.1 SDP扩展属性定义
   6.2 字段子集协商流程
   6.3 交互模式声明
   6.4 会话中途重新协商

7. 传输保护机制
   7.1 跨包冗余保护
   7.2 弱网字段裁剪
   7.3 锚点信息容错

8. 合规性要求
   8.1 发送端要求
   8.2 接收端要求
   8.3 信令协商要求

9. 安全考量

附录A（规范性）字段值注册表
附录B（资料性）典型应用场景示例
附录C（资料性）参考实现方案
```

## 四、专利交底书是否需要修改？

### 4.1 结论：专利交底书本身不需要修改，但需要"派生"出标准提案版本

**原因：**

| | 专利交底书 | 标准提案 |
|---|---|---|
| **法律保护** | 需要保护具体实现方案 | 需要定义通用规范 |
| **公开程度** | 公开后成为专利文献 | 公开后成为标准文献 |
| **策略关系** | 标准提案中引用的技术，如果已被专利覆盖，则标准实施者需要获得专利许可（FRAND承诺） |

### 4.2 正确策略：专利先行，标准跟进

```
时间线:
  
  [现在]                    [3-6个月后]              [6-12个月后]
     │                          │                         │
     ▼                          ▼                         ▼
  提交专利申请               提交AVS需求文档          提交AVS标准规范提案
  (保护具体实现)             + 技术报告               (基于专利技术方案抽象)
     │                     (建立技术影响力)           │
     │                          │                     │
     └──────────────────────────┴─────────────────────┘
                              │
                    FRAND许可承诺（如标准采纳了专利中的技术）
```

### 4.3 标准提案中需要"脱敏"的内容

以下内容在专利交底书中需要保留（保护细节），但在标准提案中需要**泛化或移除**：

| 交底书内容 | 标准提案处理 |
|-----------|------------|
| "滑动时间窗口500ms" | 不指定具体窗口大小，只定义字段语义 |
| "SurfaceFlinger postFrame钩子" | 不指定实现方式，只定义字段值的语义 |
| "应用包名映射场景类型" | 不指定映射算法，只定义场景类型枚举值 |
| "积压量32KB阈值" | 不指定阈值，只定义容灾机制框架 |
| "clientSeq应用层序号" | 泛化为"指令序列标识"，不限定实现 |
| "GCC/BBR拥塞控制" | 泛化为"拥塞控制算法"，不限定具体算法 |

### 4.4 标准提案中需要"新增"的内容

以下内容专利交底书没有，但标准提案必须有：

| 新增内容 | 说明 |
|---------|------|
| **字段值注册表（Registry）** | 定义字段值的分配、注册和扩展规则（类似IANA registry） |
| **向前/向后兼容规则** | 旧终端收到新字段如何处理、新终端收到旧字段如何处理 |
| **安全考量** | 扩展字段是否引入新的攻击面（如伪造AnchorSeq注入虚假信息） |
| **多编解码器兼容** | 不仅限于H.264/H.265，还要考虑AVS编码的场景 |
| **互操作性测试用例** | 定义测试方法验证不同实现的互通性 |

## 五、提案策略建议

### 5.1 短期（1-3个月）

1. **提交专利申请**（V2交底书）
   - 保护具体实现方案
   - 申请日期越早，优先权日越早

2. **准备AVS需求文档**
   - 从交底书中抽取"应用场景"和"传输需求"部分
   - 泛化为通用的"交互式远程渲染"场景
   - 提交给AVS系统组

### 5.2 中期（3-6个月）

3. **准备技术报告**
   - 包含完整的方案描述和实验数据
   - 在AVS工作组会议上做技术报告
   - 建立技术影响力和同行认可

4. **寻找联盟单位**
   - 联系其他云手机/云游戏厂商（如红手指、多多云、网易云游戏等）
   - 联合提案比单独提案更容易通过
   - 特别是与已有AVS会员单位合作

### 5.3 长期（6-12个月）

5. **提交标准规范提案**
   - 基于技术报告的反馈，完善标准规范草案
   - 作为GB/T 33475.6的增补件或新标准项目提交
   - 做好FRAND许可承诺准备

6. **持续迭代**
   - 根据AVS工作组的讨论意见修改提案
   - 补充互操作性测试结果
   - 争取成为标准编辑人（Editor）

### 5.4 AVS对接入口

根据AVS官网（avs.org.cn），提案提交流程：
1. 成为AVS工作组成员单位
2. 通过工作组会议提交技术提案
3. 参加系统组的定期会议（通常每季度一次）
4. 提案通过工作组评审后进入标准制定流程

## 六、总结

| 问题 | 回答 |
|------|------|
| 专利交底书需要修改吗？ | **不需要**。V2版本作为专利申请已经完整。 |
| 需要另写标准提案吗？ | **需要**。从交底书中"派生"出标准提案版本，做泛化和脱敏。 |
| 标准提案的核心差异是什么？ | 去除实现细节、增加合规性定义、增加注册表、泛化术语、引用RFC/GB标准 |
| 先做哪个？ | **专利先行**（保护优先权日），然后需求文档（占位），最后标准规范 |
| 建议标准标题 | 《智能媒体传输 补充件：交互式远程渲染传输协议扩展》 |
| 对接AVS哪个标准 | GB/T 33475.6-2024（智能媒体传输）最为合适 |
