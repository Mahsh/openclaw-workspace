## 一、整体架构：为什么是这四个文件？

```
tech-research/
├── SKILL.md                  ← 大脑（流程调度）
├── scripts/
│   └── report_template.md    ← 骨架（输出约束）
├── references/
│   └── research_guide.md     ← 方法论（检索策略）
└── assets/
    └── radar_sources.json    ← 数据源（可维护配置）
```

**核心设计原则：关注点分离** — 流程调度、输出格式、检索策略、数据配置各司其职，修改一个不影响其他。这也是 OpenClaw Skill 框架推荐的目录规范。

## 二、SKILL.md — 核心调度文件

### 2.1 Frontmatter（元数据）

```yaml
---
name: tech-research
description: "技术调研智能体：自动检索、并行调研、结构化输出调研报告"
user-invocable: true
allowed-tools:
  - web_search
  - web_fetch
  - sessions_spawn
  - sessions_yield
  - write
  - read
---
```

| 字段 | 为什么这么写 | 答辩要点 |
|------|-------------|---------|
| `name` | Skill 的唯一标识，OpenClaw 用它做触发和路由 | "这是 Skill 的身份证" |
| `description` | 一句话告诉 LLM 这个 Skill 能做什么，**必须引号包裹** | "触发判断的依据，关键词：自动检索、并行、结构化" |
| `user-invocable: true` | 允许用户通过关键词直接触发，而非只由系统调度 | "体现用户可主动调用，不是纯后台任务" |
| `allowed-tools` | **最小权限原则**，只授予调研所需的6个工具 | "安全设计：不授予 exec/browser 等高危工具权限" |

**🎤 答辩话术：** "SKILL.md 是 Skill 的入口文件，包含 YAML 元数据和工作流程定义。我们采用最小权限原则，只开放了 web_search、web_fetch、sessions_spawn、sessions_yield、write、read 这六个工具——调研不需要执行代码或操作浏览器。"

### 2.2 三种工作模式

```
模式一：单点深度调研 → 串行执行，适合单一技术点
模式二：多点并行调研 → sessions_spawn 并行子Agent，适合技术选型
模式三：技术雷达     → cron 定时触发，适合持续跟踪
```

**🎤 答辩话术：**

> "我们设计了三种调研模式来覆盖不同场景：
> - **单点调研**用串行方式，先搜索→再抓取→再整理，适合'帮我查一下XX'这类问题
> - **并行调研**用 `sessions_spawn` 启动多个子Agent同时工作，适合'对比方案A和方案B'
> - **技术雷达**通过 `cron` 定时任务每周自动扫描技术动态，实现被动信息获取"

**🎤 追问应对：为什么不用一个模式解决所有问题？**
> "因为不同场景对**延迟和成本**的要求不同。单点调研如果也启动子Agent，开销太大；并行调研如果串行做，用户等待时间太长。技术雷达是后台任务，不需要用户交互。"

### 2.3 触发场景设计

```yaml
触发关键词：
- "调研"、"技术调研"、"技术预研"、"技术选型"
- "查一下XX技术"、"对比一下XX方案"
- "技术雷达"、"技术动态"
```

> "触发关键词设计覆盖了**正式用语**（技术调研、技术选型）和**口语化表达**（查一下、对比一下），降低用户学习成本。OpenClaw 的 Skill 系统会基于 description 和关键词自动匹配触发。"

## 三、scripts/report_template.md — 输出约束

### 3.1 为什么单独做一个模板文件？

> "模板文件的作用是**约束 LLM 的输出格式**。如果不给模板，每次调研生成的报告结构会不一致，后续无法做批量对比或索引。这个文件在 Skill 被触发时作为参考加载，确保每次输出结构一致。"

### 3.2 六大章节的设计逻辑

| 章节 | 为什么要 | 答辩价值 |
|------|---------|---------|
| **一、背景与目标** | 回答"为什么调研"，不是"调研了什么" | 避免报告变成纯知识罗列 |
| **二、技术概述** | 核心原理+发展现状，快速建立认知 | 评委看这里就能判断技术是否合适 |
| **三、方案对比** | **表格强制**，2-3个方案横向对比 | 体现工程决策思维 |
| **四、落地建议** | 推荐方案+实施路径+预期收益 | "不是论文，是工程报告" |
| **五、风险与局限** | 诚实评估，不是只说优点 | 体现技术判断力 |
| **六、参考资料** | 必须含 URL，可追溯 | 保证可验证性 |

**🎤 答辩话术：**
> "我们设计的报告模板遵循了**工程调研报告**的范式，而非学术论文范式。核心差异是：必须有落地建议、必须有方案对比、必须标注来源。这样生成的报告可以直接用于团队技术决策，而不只是知识积累。"

### 3.3 格式要求为什么这么细？

```markdown
- 方案对比必须用表格 → 结构化对比，而非段落描述
- 事实性陈述标注来源 → 可追溯，不是 AI 编造
- 落地建议必须结合云手机场景 → 避免泛泛而谈
- 报告总长度建议 2000-4000 字 → 控制信息密度
```

> "这些约束是为了**控制 LLM 的输出质量**。没有约束，LLM 容易写出'正确但无用'的泛泛内容。比如'落地建议必须结合云手机场景'这条，强迫 AI 思考这个技术在云手机里怎么用，而不是给一个通用建议。"

## 四、references/research_guide.md — 检索方法论

### 4.1 为什么需要方法论指南？

> "LLM 默认搜索时只会搜英文关键词。这个文件教 AI **中英文双语搜索**、**信息源优先级**、**质量判断标准**，提升调研的系统性。"

### 4.2 核心设计

#### 信息源优先级

```
官方文档 > GitHub仓库 > 技术博客 > 论文 > 社区讨论
```

> "官方文档最权威但可能不够深入，技术博客有实战经验但可能有偏见，社区讨论有真实反馈但噪音多。这个优先级指导 AI 先抓权威来源，再补充实战信息。"

#### 质量判断标准

```
✅ 有具体数据/实验结果      ❌ 纯搬运无原创观点
✅ 作者有相关领域背景        ❌ 无来源的断言
✅ 发布时间在 2 年内
```

> "这是教 AI 做**信息质量筛选**。没有时间判断，AI 可能会引用 10 年前的过时技术；没有来源要求，AI 可能会引用不可靠的博客。"

#### 调研深度控制

```
快速调研（1h内）：3-5 篇资料
标准调研（2-4h）：8-12 篇资料  ← 默认
深度调研（1天+）：15+ 篇资料
```

> "这是**成本与质量的平衡**。不是每次调研都需要深度报告，默认标准调研覆盖 80% 的场景。用户可以说'快速调研'或'深度调研'来调整。"

#### 云手机领域关注点

```
端到端延迟、带宽适应性、ARM/x86兼容性、虚拟化开销、音视频同步、弱网表现
```

> "这是**领域特化**。通用技术调研 Skill 不会有这些关注点，我们针对云手机场景做了定制，确保调研时不会遗漏关键维度。"

## 五、assets/radar_sources.json — 技术雷达数据源

### 5.1 为什么用 JSON 配置文件？

> "把数据源抽成 JSON 配置文件的好处是**无需修改代码即可维护**。新增一个关注领域，只需要在 JSON 里加一个 source 条目，Skill 逻辑不需要变。这是**配置与逻辑分离**的设计模式。"

### 5.2 六大关注源的选择逻辑

| 源 | 为什么关注 | 与云手机的关系 |
|----|----------|--------------|
| WebRTC 官方 | 实时通信的核心协议 | 云手机视频流传输基础 |
| 音视频编解码 | H.265/AV1/VVC 演进 | 直接影响编码质量和带宽 |
| 云游戏/云手机 | 竞品动态 | 行业趋势跟踪 |
| 虚拟化技术 | KVM ARM、容器化 | 云手机底层基础设施 |
| 传输协议 | QUIC/WebTransport | 下一代低延迟传输 |
| AI/大模型 | LLM、智能体 | AI增强音视频的方向 |

### 5.3 filter_rules 的设计

```json
"filter_rules": {
  "include": ["云手机", "音视频", "低延迟", "虚拟化", "ARM", "WebRTC"],
  "exclude": ["广告", "招聘", "纯新闻无技术内容"]
}
```

> "Include/Exclude 双规则过滤噪音。技术雷达如果不过滤，每周会收到大量无关信息。Include 保证相关性，Exclude 过滤低价值内容。"

## 六、答辩常见 Q&A 准备

### Q1: 为什么选择 OpenClaw Skill 而不是自己写脚本？

> "OpenClaw Skill 提供了**标准化的触发机制、工具权限管理、子Agent编排能力**。自己写脚本需要解决调度、权限、并行等基础设施问题，而 Skill 框架让我们专注于调研逻辑本身。"

### Q2: 并行调研怎么保证质量一致？

> "每个子Agent收到的任务描述都包含**相同的报告模板**（report_template.md），输出结构一致。主 Agent 在汇总时做质量检查和交叉验证。"

### Q3: 如果搜索结果不够怎么办？

> "research_guide.md 中定义了**信息源优先级和深度控制**。如果标准调研不够，可以升级为深度调研（15+篇资料）。同时中英文双语搜索确保覆盖更全面。"

### Q4: 技术雷达怎么保证不推送垃圾信息？

> "radar_sources.json 中的 filter_rules 做双重过滤：include 保证与云手机相关，exclude 过滤广告/招聘/纯新闻。同时人工维护数据源列表，确保源头质量。"

### Q5: 这个 Skill 可以复用到其他领域吗？

> "可以。只需修改三个地方：① SKILL.md 中的触发关键词和领域描述；② references/research_guide.md 中的'云手机领域关注点'；③ assets/radar_sources.json 中的数据源。核心流程不变。"

### Q6: 调研报告的准确性如何保证？

> "三重保障：① 事实性陈述必须标注来源 URL；② 优先抓取官方文档而非博客；③ 方案对比要求多维度表格，避免主观偏断。同时报告归档到 memory/research/ 目录，可持续追溯和复查。"
