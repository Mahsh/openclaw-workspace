## P1：基于RTP扩展的交互模式感知传输保护方法

### 发明名称
一种基于RTP扩展的交互模式感知传输保护方法及系统

### 要解决的技术问题

在云手机等交互式远程渲染系统中，终端接收端对下行视频流的传输保护策略（FEC冗余度、NACK重传次数和等待时间）采用固定配置，无法根据当前交互场景动态调整。

具体问题：
- 用户在玩动作游戏时（高频触摸），丢一帧可能错过关键画面，但终端仍用默认FEC策略
- 用户在打字输入时（低频键盘），丢一帧影响很小，但终端仍用相同的重传策略，浪费带宽
- 标准WebRTC的FEC/NACK策略设计面向通用音视频通话，不理解"交互上下文"

### 核心技术方案

**1. 上行指令聚合分类器**

云端维护滑动时间窗口（默认500ms），统计窗口内的指令类型和频率，输出交互模式分类：

```
上行指令流 → opttype解析 → 基础分类 → 滑动窗口统计 → 交互模式分类
```

分类结果编码为8 bit的IM字段值。

**2. RTP Header Extension注入IM字段**

云端编码器在每帧编码时查询聚合分类器，将IM值写入RTP Header Extension。每一帧的所有RTP包均携带IM（非仅首包），确保丢包后终端仍可从相邻帧获取交互模式。

**3. 终端差异化传输保护**

```
收到RTP包 → 解析IM字段 → 查询传输保护策略表

IM=0x01 (HIGH_FREQ):
  - FEC冗余率: 基准 × 1.5
  - NACK最大重传: 4次 (默认2次)
  - NACK等待时间: 15ms (默认30ms)
  - 效果: 激进保护，宁可多用带宽也要保证每帧到达

IM=0x03 (KEY_INPUT):
  - FEC冗余率: 基准 × 0.5
  - NACK最大重传: 1次
  - NACK等待时间: 50ms
  - 效果: 保守保护，节省带宽给后续帧

IM=0x00 (NONE):
  - 默认策略
```

### 区别于现有技术的关键点

| 现有技术 | 本发明 |
|---------|-------|
| FEC/NACK策略固定或仅基于网络指标调整 | 基于交互模式分类动态调整 |
| RTP不携带交互上下文 | RTP扩展携带IM字段 |
| 不理解"用户正在做什么" | 聚合分类器实时判断交互模式 |

### 独立权利要求

一种交互式远程渲染流媒体系统的传输保护方法，其特征在于：
- 服务端维护滑动时间窗口，统计窗口内上行交互指令的类型和频率，计算交互模式分类标识；
- 服务端在每帧的RTP头部扩展中携带所述交互模式分类标识；
- 终端接收端根据所述交互模式分类标识，从预定义的策略表中查询对应的FEC冗余度和NACK重传参数，应用于当前帧的传输保护。

### 预估壁垒强度
⭐⭐⭐⭐ — "交互模式分类→传输策略映射"这个逻辑链条在现有云手机/WebRTC专利中几乎没有覆盖。聚合分类器的滑动窗口设计增加了实现细节的壁垒。

## P2：基于渲染管线钩子的端到端交互延迟测量方法

### 发明名称
一种基于渲染管线钩子的端到端交互延迟测量方法及系统

### 要解决的技术问题

在云手机系统中，精确测量"用户操作发出→对应画面呈现"的端到端延迟是优化体验的基础，但现有方案面临三大难题：

1. **时钟不同步**：终端和云端没有NTP同步，无法直接比较两端时间戳
2. **指令-帧关联困难**：云端渲染管线（指令到达→SurfaceFlinger渲染→编码器出帧）存在不可控延迟，不同APP响应速度不同，无法简单地将"某条指令"和"某一帧"绑定
3. **TCP序列号不可用**：TCP seq是协议栈内部管理的，应用层不一定能直接获取

### 核心技术方案

**1. 应用层指令序号**

终端在每条上行指令中嵌入应用层自增序号 `clientSeq`（替代TCP seq）。

**2. 渲染管线钩子（核心创新）**

在Android SurfaceFlinger的 `postFrame` 回调中插入钩子：

```
指令到达(TCP) → 指令追踪器记录pending_seqs
                    ↓
渲染引擎渲染 → SurfaceFlinger postFrame
                    ↓
           钩子: 取出max(pending_seqs) → 作为CSA
                    ↓
编码器编码帧 → CSA写入RTP Header Extension
                    ↓
RTP发送到终端
```

关键设计：**取"自上一帧以来所有被消费指令中最大的seq"**，而非试图精确绑定"哪条指令对应哪一帧"。

**3. 终端无时钟同步延迟计算**

```
终端: 发送指令(clientSeq=N) → 记录 T_send(N)     [终端本地时钟]
终端: 收到帧(CSA=N)         → 记录 T_recv(N)     [终端本地时钟]
延迟 = T_recv(N) - T_send(N)
```

全程在终端本地时钟体系内完成，无需任何时钟同步。

**4. 不同APP响应差异的自然包含**

如果某APP响应慢（指令到达后500ms才渲染），CSA关联到500ms后的帧，测出的延迟就是500ms+传输延迟。这正是真实端到端体验延迟，不需要额外修正。

**5. 特殊情况处理**

| 情况 | 处理 |
|------|------|
| 一帧消费多条指令 | CSA取max(seq) |
| 无新指令的帧 | CSA=0，不参与统计 |
| 同一指令影响多帧 | 仅首帧关联CSA |
| CSA包丢失 | 使用最近锚点估算（置信度LOW） |

### 区别于现有技术的关键点

| 现有技术 | 本发明 |
|---------|-------|
| NTP时钟同步后比较两端时间戳 | 无需时钟同步，纯终端本地计算 |
| 只测量"网络传输延迟"（RTP单向） | 测量完整"操作→画面"链路 |
| 指令和帧通过时间戳近似关联 | 渲染管线钩子实现因果关联 |
| 不同APP响应差异需额外修正 | 差异被自然包含在测量结果中 |

### 独立权利要求

一种交互式远程渲染流媒体系统的端到端延迟测量方法，其特征在于：
- 终端在上行交互指令中嵌入应用层自增序列标识；
- 服务端在渲染管线的帧提交回调中插入钩子，取出"自上一帧渲染以来所有被渲染系统消费的上行指令中最大的序列标识"作为锚点值；
- 服务端将所述锚点值写入下行RTP头部扩展字段；
- 终端通过比较发送指令时的本地时间戳与收到对应锚点帧时的本地时间戳，计算端到端交互延迟，无需终端与服务端之间的时钟同步。

### 预估壁垒强度
⭐⭐⭐⭐⭐ — "渲染管线钩子+因果关联+无时钟同步"的组合是高度原创的。现有云手机专利几乎没有涉及"指令-帧关联"这个技术难点，更不用说在渲染管线中插入钩子的具体实现。这是专利墙中壁垒最强的一件。

## P3：基于帧语义标记的场景化播放策略方法

### 发明名称
一种基于帧语义标记的场景化播放策略方法及系统

### 要解决的技术问题

标准WebRTC的Jitter Buffer策略只关注网络传输抖动，不区分视频帧的内容属性。但在云手机场景下，不同内容的帧对播放策略的要求完全不同：

- **游戏战斗帧**：必须尽快渲染，宁可画质抖动也要跟手（低延迟优先）
- **文档阅读帧**：必须文字清晰，允许适当延迟（清晰度优先）
- **视频播放帧**：必须连续流畅，允许缓冲（流畅度优先）
- **静态帧**：可以充分等待，直到收到完整帧（完整性优先）

现有协议没有机制将"帧的内容属性和紧急程度"从云端传递给终端。

### 核心技术方案

**1. FIT字段定义（场景类型 + 紧急等级）**

8 bit FIT字段，高4位场景类型 + 低4位紧急等级：

```
场景类型(4bit):
  0x0=ACTION  0x1=EXPLORATION  0x2=TEXT_UI
  0x3=VIDEO   0x4=TRANSITION   0x5=STATIC

紧急等级(4bit):
  0-3=LOW  4-7=MEDIUM  8-11=HIGH  12-15=CRITICAL
```

**2. 场景类型识别（云端）**

云端渲染引擎/窗口管理器检测当前前台应用的包名/Activity，通过映射表确定场景类型。映射规则可热更新。

```
com.tencent.tmgp.sgame → ACTION
com.tencent.mm (聊天)  → TEXT_UI
com.youku.phone       → VIDEO
锁屏/待机              → STATIC
```

**3. 紧急等级判定（云端）**

云端根据系统负载和网络状态综合判断紧急等级：
- 检测到密集操作 + 低网络延迟 → 高紧急
- 画面变化小 + 高网络抖动 → 低紧急
- 关键操作响应帧（如紧急停止） → 极紧急

**4. 终端Jitter Buffer自适应**

```python
def adjust_jitter_buffer(fit):
    scene = fit >> 4
    urgency = fit & 0x0F
    
    # 基础深度由场景决定
    base = {ACTION: 1, EXPLORATION: 3, TEXT_UI: 4, VIDEO: 7, STATIC: 10}[scene]
    
    # 紧急等级削减深度
    actual = max(0, base - urgency)
    return actual
```

效果：
- ACTION + CRITICAL → max(0, 1-15) = 0帧缓冲 → 立即渲染
- TEXT_UI + LOW → max(0, 4-2) = 2帧缓冲 → 清晰度优先
- VIDEO + MEDIUM → max(0, 7-5) = 2帧缓冲 → 适度缓冲

### 区别于现有技术的关键点

| 现有技术 | 本发明 |
|---------|-------|
| Jitter Buffer只看网络抖动 | 同时看帧内容属性和紧急程度 |
| 所有帧一视同仁 | 不同场景类型用不同策略 |
| 无法知道"这帧是什么内容" | FIT字段携带场景语义 |
| 场景识别在终端侧（计算受限） | 场景识别在云端（信息完整） |

### 独立权利要求

一种交互式远程渲染流媒体系统的播放策略方法，其特征在于：
- 服务端根据当前渲染内容识别场景类型，根据系统状态判定渲染紧急等级，将两者编码为帧意图标记写入RTP头部扩展；
- 终端接收端解析所述帧意图标记，根据场景类型确定基础缓冲深度，根据紧急等级动态缩减缓冲深度，实现场景化的Jitter Buffer自适应策略。

### 预估壁垒强度
⭐⭐⭐ — "场景类型→缓冲深度映射"这个概念较直觉，可能被现有技术部分覆盖。壁垒主要在FIT字段的双子字段设计（场景+紧急度联合编码）和具体的映射策略上。建议结合具体的映射算法和阈值来增强壁垒。

## P4：基于RTCP扩展的上行通道状态反馈与自适应方法

### 发明名称
一种基于RTCP扩展的上行通道状态反馈与终端自适应方法及系统

### 要解决的技术问题

在云手机的非对称双链路架构中，上行TCP控制链路和下行RTP媒体链路是独立的。当上行TCP发生拥堵时：

- 用户操作指令积压在终端的TCP发送队列中
- 云端收不到新指令，但仍按旧状态推送画面
- 终端不知道上行已堵，看到的画面在响应"过时的操作"
- 结果：操作和画面严重不同步，用户感觉"控制不了手机"

现有WebRTC/RTCP协议没有任何机制让服务端向终端反馈"上行控制通道的健康状况"。

### 核心技术方案

**1. 设计动机：为什么用RTCP而不是RTP**

上行状态反馈是**控制面信息**（"通道是否通畅"），不是逐帧需要携带的**媒体元数据**。放在RTP Header Extension中属于语义错配，且增加每包开销。RTCP天然就是传输控制反馈的通道，发送频率（2-4次/秒）足够满足上行状态感知需求。

**2. RTCP APP报文定义**

采用RTCP APP报文类型（PT=204），自定义name为"CPUS"（Cloud Phone Uplink Status）：

```
| USF主字段(8bit) | USF辅助字段(8bit) | Reserved(16bit) |

USF主字段:
  0x00 = NORMAL
  0x01-0x0F = MILD_LAG
  0x10-0x3F = MODERATE_LAG
  0x40-0xFE = SEVERE_LAG
  0xFF = OUTAGE

USF辅助字段:
  最近一次指令接收间隔 / 10ms
```

**3. 云端状态计算方法**

基于"指令接收间隔 + 活跃状态检测"的双重判断：

```python
class UplinkMonitor:
    ACTIVITY_WINDOW = 5000ms   # 活跃判断窗口
    MILD_THRESH = 500ms        # 轻度滞后阈值
    SEVERE_THRESH = 2000ms     # 严重滞后阈值
    
    def compute(self):
        if is_active and (now - last_recv) > MILD_THRESH:
            return 上行拥堵状态
        else:
            return NORMAL  # 用户可能没在操作
```

核心逻辑：只有"用户明显在操作但指令突然不来了"才判定为拥堵。用户不操作时不会误报。

**4. RTCP发送策略**

- 常规：每500ms发送一次
- USF值变化时：立即发送（不等周期）
- 连续3次未变化：降至每2秒一次
- 弱网可通过SDP协商关闭

**5. 终端自适应策略**

```
收到RTCP APP(CPUS):
  NORMAL:       不干预
  MILD_LAG:     不干预，记录日志
  MODERATE_LAG: 适当降低Jitter Buffer深度
  SEVERE_LAG:   大幅降低Jitter Buffer + 请求降帧率 + 提示用户
  OUTAGE:       最小缓冲 + 显示网络警告
```

### 区别于现有技术的关键点

| 现有技术 | 本发明 |
|---------|-------|
| 上行状态对下行不可见 | 服务端通过RTCP反馈上行健康度 |
| RTCP只反馈网络传输质量 | RTCP扩展反馈控制链路状态 |
| 终端无法区分"用户没操作"和"操作到不了" | 活跃状态检测避免误报 |
| 上行拥堵时画面继续正常推送 | 终端感知拥堵后主动调整播放策略 |

### 独立权利要求

一种交互式远程渲染流媒体系统的上行通道状态反馈方法，其特征在于：
- 服务端监控上行控制链路的指令接收状态，当检测到终端处于活跃交互状态但指令接收间隔超过预设阈值时，生成上行状态反馈信息；
- 服务端通过RTCP应用定义报文将所述上行状态反馈信息发送至终端；
- 终端解析所述RTCP报文，根据上行状态等级采取相应的播放策略自适应措施。

### 预估壁垒强度
⭐⭐⭐⭐ — "上行通道状态通过RTCP反馈"这个概念在云手机/WebRTC领域是全新的。现有RTCP反馈（REMB、Transport-CC、NACK）全部面向网络传输质量，没有人用RTCP反馈控制链路状态。"活跃状态检测避免误报"的逻辑增加了实现壁垒。

## P5：面向交互式流媒体的SDP动态协商与弱网自适应方法

### 发明名称
一种面向交互式远程渲染流媒体的SDP动态协商与弱网自适应方法及系统

### 要解决的技术问题

在云手机系统中，RTP扩展元数据字段在弱网条件下会产生额外的协议开销。当丢包率>10%时，每个RTP包多携带6-8字节的扩展头部会加剧丢包和延迟。同时，弱网场景下并非所有元数据字段都同等重要——延迟测量锚点（CSA）比交互模式标识（IM）更关键。

现有WebRTC的SDP协商机制不支持RTP扩展字段的动态子集选择和运行时调整。

此外，上行TCP严重拥堵时，关键交互指令可能延迟数秒到达云端，需要容灾传输通道。

### 核心技术方案

**1. SDP字段子集协商**

通过自定义SDP属性声明启用哪些RTP扩展字段：

```
全量:  a=irrm-fields: IM,CSA,FIT         // 正常网络
精简:  a=irrm-fields: CSA               // 弱网（仅保留锚点）
中间:  a=irrm-fields: CSA,FIT            // 中度弱网
```

通过SDP re-offer/answer动态切换，无需中断WebRTC会话。

**2. 弱网触发条件**

```
丢包率 > 10%:  触发精简模式（仅CSA）+ 启用上行容灾
丢包率 > 5%:   触发中间模式（CSA+FIT）
丢包率 < 5% 持续3秒: 恢复全量模式
```

**3. RTCP USF动态开关**

```
正常:  a=irrm-usf-rtcp: enabled
弱网:  a=irrm-usf-rtcp: disabled    // 关闭USF RTCP减少RTCP开销
```

**4. 跨包冗余保护**

每N帧（默认30帧）定义一个锚点帧，携带完整字段；普通帧至少携带CSA：

```
锚点帧:  IM + CSA + FIT (完整)
普通帧:  CSA only (最小化)
```

锚点丢失时终端使用最近锚点估算延迟（置信度降级）。

**5. 上行双通道容灾**

```
触发: TCP发送队列积压量连续3×200ms > 32KB

关键指令同时走:
  主通道:   TCP Socket
  容灾通道: WebRTC DataChannel (unordered, no-retransmit)

云端: SequenceID去重，取先到者
```

**6. 交互模式SDP声明**

```
a=irrm-session-mode: action          // 影响云端默认编码Profile
a=irrm-latency-budget: 80            // 延迟预算
```

模式变更时通过re-offer切换编码策略。

### 区别于现有技术的关键点

| 现有技术 | 本发明 |
|---------|-------|
| RTP扩展字段全有或全无 | 字段子集可动态选择 |
| 弱网只降码率/帧率 | 弱网同时裁剪协议开销+启用容灾 |
| SDP一次性协商，运行时不变 | SDP re-offer动态调整 |
| 控制指令只走TCP | TCP+DataChannel双通道容灾 |

### 独立权利要求

一种交互式远程渲染流媒体系统的弱网自适应方法，其特征在于：
- 在SDP中定义扩展字段子集声明属性，支持通过SDP重新协商动态调整RTP扩展字段的使用子集；
- 终端根据网络状况指标触发字段子集切换，弱网条件下缩减为关键字段子集以减少协议开销；
- 定义锚点帧和普通帧的跨包冗余机制，弱网下保证关键锚点信息的可靠传递；
- 当上行控制通道发生严重拥堵时，关键交互指令同时通过备用传输通道发送，服务端通过序列标识去重取先到者。

### 预估壁垒强度
⭐⭐⭐ — SDP动态协商和弱网自适应的概念相对通用，壁垒主要在"字段子集选择策略"和"跨包冗余+双通道容灾的组合"上。建议重点强调字段子集与网络状况指标的联动策略，以及锚点帧/普通帧的具体设计。

## 5件专利的申请策略

### 时间规划

```
第1周:    P1 + P2 + P3 同时提交（核心三件，同日申请）
第5周:    P4 提交（依赖P2的延迟测量基础）
第8周:    P5 提交（系统级，整合前4件）
```

### 为什么P1/P2/P3同日申请

- 三者是并行独立的技术点，互不依赖
- 同日申请确保优先权日一致
- 如果审查中出现交叉引用问题，同日申请更容易处理

### 防御策略

| 场景 | 应对 |
|------|------|
| 竞品绕开P1（改FEC策略映射表） | P2/P3/P4仍然覆盖，且P5覆盖系统级方案 |
| 竞品绕开P2（用时钟同步替代） | P1/P3独立有价值，且P5覆盖弱网场景 |
| 某件专利被无效化 | 其他4件仍然构成防御网络 |
| 竞品整体照搬 | 5件全部侵权，赔偿最大化 |

### 与AVS标准的关系

| 专利 | 对应标准提案章节 |
|------|----------------|
| P1 | 第6.3节（IM字段） |
| P2 | 第6.4节（CSA字段） |
| P3 | 第6.5节（FIT字段） |
| P4 | 第6.6节（USF RTCP报文） |
| P5 | 第7章（SDP协商）+ 第8章（传输保护） |

如标准采纳了上述技术，需在AVS工作组做FRAND许可承诺。
